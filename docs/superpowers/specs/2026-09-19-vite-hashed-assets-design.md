# Vite and content-hashed frontend assets

**Status:** Draft — self-reviewed; independent refinement pending

## Goal and approved scope

Build the existing vanilla JavaScript, multi-page frontend with Vite. Changed application assets receive new URLs. Use exactly the same build artifact in every environment; deployment supplies public runtime configuration. Keep the current successful frontend release plus one previous successful release. Cleanup runs only after successful publication and verification. Tabs from older releases may need refreshing after their assets are pruned.

No TypeScript conversion, UI framework, SPA routing, new staging infrastructure, authentication redesign, API contract changes, or database changes. Cleanup is limited to superseded asset-loading/build/deployment code. Existing unrelated working-tree changes are not part of this work.

## Current architecture

- `src/web/` contains static HTML, CSS and native JavaScript modules, without a frontend package/build configuration.
- `src/web/js/api.js` and `auth.js` import the generated `config.js` ES module. Login, callback and logout pages also contain inline module scripts.
- `api/templates/base.html`, `recipe.html` and `ingredient.html` render HTML through `api/routes/pages.py`. The base template references source CSS; recipe pages additionally reference source JavaScript. Ingredient and 404 pages inherit the base stylesheet links.
- `infrastructure/ansible/playbooks/deploy.yml` copies frontend sources and generates environment-specific `web/js/config.js`.
- `infrastructure/scripts/deploy-cutover.sh` locks deployment, backs up, builds the API image, stops writers, runs migrations, starts/checks the API, then publishes the frontend by moving directories. The new API can render pages before that final publication.
- Both Caddy configurations currently revalidate unversioned HTML/JS/CSS. The Ansible template and standalone configuration must remain aligned.
- Analytics loads D3 from a CDN. This migration leaves that dependency unchanged; content-hashing guarantees apply to application build assets, not that external resource.

## Build and runtime configuration

Add a root npm manifest and committed lockfile, a small `vite.config.mjs` multi-page configuration, and `dev`, `build`, and `preview` commands. Omit root `type: module` to preserve existing CommonJS `.js` tests. Add explicit `.gitignore` exceptions for package.json and package-lock.json because the repository ignores JSON files broadly, and ignore `node_modules/`. Set Vite `appType: 'mpa'` to avoid SPA fallbacks hiding missing routes. Select a supported, vetted Vite release compatible with the repository's tested Node 22.22.2 and document its actual Node requirement. Build output is ignored `dist/`, never tracked source changes.

All existing static HTML pages are build entrypoints, preserving their URLs. Vite processes their module scripts (including inline modules) and local stylesheet links, including root-absolute links resolved against `src/web` as the Vite project root. Do not move application CSS into Vite's public directory, whose contents bypass processing. Explicit additional inputs cover server-rendered page JavaScript and CSS. Emit Vite's manifest; keep entry identifiers stable and verify them against real build output. Move robots.txt, llms.txt, site.webmanifest and img/ into `src/web/public/`, keeping their existing root URLs unchanged through Vite's public-directory copy behavior. This preserves relative icon URLs inside site.webmanifest without rewriting its contents. Update the existing Git ignore exceptions for robots.txt and llms.txt to their new public/ locations. Do not put application JS/CSS in public/ or copy the source JS tree into production. Set the build manifest path explicitly and exclude manifest/inventory metadata from the served HTML tree; metadata remains in the deployment artifact and retained release records.

Use a fixed `/js/config.js` runtime ES-module URL, excluded from bundling. Preserve the existing relative source imports for native Node tests and local development. In Vite's build, resolve only the exact source config module to an external module and map its emitted import specifier to `/js/config.js` (using the bundler's external/output-path facilities). Verify the real built import text; do not externalize unrelated config filenames or emit an absolute filesystem path. Vite development serves the locally generated file at that URL. Production deployment supplies the file separately; it is absent from the reusable build artifact. Do not bake environment configuration into Vite variables or bundled code. ES-module dependency evaluation ensures configuration is loaded before its consumers, without an async bootstrap framework.

Preserve the current configuration fields and default export. Generate values with JSON serialization rather than interpolating raw strings into JavaScript. Validate required fields and public URL values during deployment before cutover, and fail clearly on missing configuration. No credential, client secret, or database value may enter the public file. Adapt `scripts/generate_config.py`, `scripts/local-config.sh`, and the Ansible template consistently. Existing API/auth Node tests retain their relative-import config stubs; new build checks independently verify runtime externalization. For `preview`, use a disposable copy of the artifact with explicitly generated public config at js/config.js; never inject config into the reusable artifact itself.

## Server-rendered asset resolution

Package the build's manifest in the API image from the same staged artifact; do not have the running API read a mutable manifest through the served web directory. Add one small asset resolver used by Jinja templates. It resolves stable entry keys, emits hashed module URLs and required stylesheet links, and follows manifest imports for dependent CSS without duplicate links. Handle CSS entries according to actual output from the pinned Vite version: a `.css` file value is a stylesheet; any `.js` file value is not a stylesheet, and associated `css` arrays supply stylesheet URLs. Do not hardcode an assumed CSS-only entry shape. Include all emitted files in the inventory, even empty JS siblings when present. Separate CSS emission for static and server-rendered entries is acceptable; test equivalent styling rather than requiring byte-identical CSS filenames. Preserve stylesheet order and module initialization order. Vite handles equivalent rewriting for static HTML.

Explicit template entry keys, relative to the Vite root, are `normalize.css`, `styles.css`, `recipe-card.css`, `js/common.js` and `js/recipe.js`. Base emits stylesheet links for normalize.css then styles.css; ingredient and 404 inherit those and add no JavaScript. Recipe additionally emits recipe-card.css and two `type="module"` script tags for common.js then recipe.js, using their manifest file URLs. Imported shared modules remain deduplicated by the module graph. Module-preload tags are not substitutes for executable entry scripts. Test these mappings against the real manifest from the pinned Vite build.

Production startup validates the manifest, required entries and safe relative asset paths; missing or malformed data is an error, never a fallback to stale source URLs. Introduce a dedicated explicit asset mode, independent of `settings.environment`, defaulting to built assets. Tests requiring source URLs must explicitly select development asset mode, including router-only tests without application lifespan. In that mode, the resolver emits root-absolute source URLs such as `/styles.css` and `/js/recipe.js`; no missing-manifest heuristic selects the mode.

Preserve the existing frontend-only local workflow: Vite listens on localhost:8000 with strict-port behavior, and generated config points to the remote dev API. Keep existing Cognito callback/logout origins unchanged. Local FastAPI/database is not required. For integrated SSR development, explicitly run FastAPI on another port (for example 8001), enable development asset mode, and configure Vite to proxy server-rendered routes to it; API traffic continues to follow runtime config. Browse SSR pages through `http://localhost:8000/recipe/...` (Vite's proxy), not directly at the backend port: root-absolute asset URLs then resolve against Vite's origin. Direct browser access to development HTML on port 8001 is not a supported asset-serving flow and requires no additional origin-injection mechanism. Runtime `appUrl` remains `http://localhost:8000`, while `apiUrl` remains the remote dev API URL; these are deliberately different. Production-like SSR checks use the built manifest and Caddy. Update `scripts/serve.sh` and local setup documentation rather than retaining competing static-server instructions.

## Asset serving and cache policy

Serve `/assets/*` from `/opt/cocktaildb/frontend-assets/`, separate from the release-specific HTML/config root. Store files directly below that directory without a second `assets/` component; Caddy strips `/assets` using `handle_path`. Create the directory before the existing pre-cutover Caddy restart; legacy routes continue using the unchanged web root at that point. Both deploy.yml and the standalone deploy-caddy.yml must establish this directory and preserve a valid existing web-root symlink rather than replacing it. A dangling web-root symlink must fail clearly, not silently initialize a different serving root. Publish assets there before starting the new API so its manifest references already resolve. Copy each asset atomically; if an existing pathname has different bytes, fail instead of overwriting an immutable URL.

Successful hashed asset responses receive `Cache-Control: public, max-age=31536000, immutable`. Apply immutable headers only to successful asset responses using status-aware response matching, not a path-only header rule. Missing assets must return a real 404 without long-lived immutable caching; no HTML fallback. Apply equivalent behavior in both domain and HTTP server blocks. HTML, server-rendered pages and `/js/config.js` revalidate with `Cache-Control: no-cache`. Unhashed public media retain a conservative short cache lifetime. Ensure the broad existing JS/CSS matchers do not overwrite hashed-asset headers, and do not change personalized API cache behavior.

## Deployment and artifact contract

Build on the deployment/controller machine, not EC2. A deployment can consume an explicitly supplied, already-built frontend artifact directory; the normal wrapper may build one when none is supplied. Ansible stages that artifact instead of `src/web/` and explicitly creates the staged js/ directory before generating runtime config. Both paths validate it before touching the live application. This supports promoting identical bytes to a second environment without rebuilding.

The artifact contains built HTML/public files, hashed assets and manifest, but no environment-specific runtime configuration. Record an inventory of all emitted `/assets/` files as part of the artifact, including transitive chunks and CSS-referenced files; retention must not rely only on top-level manifest entries. Validate inventory paths remain inside the asset directory. After the delete-enabled Stage API code synchronization, stage a copy of the matching artifact manifest at remote `api/frontend-manifest.json` within the release build context, before API image construction, so the existing `COPY api/ .` includes it at `/app/frontend-manifest.json`. Do not generate or copy this file into the controller's source api/ directory. Keep this generated file out of Git while explicitly allowing it through Docker ignore rules. Validate that the built image contains it; do not depend on ignored `dist/` or a `*.manifest` filename.

Under the existing deployment lock:

1. Validate staged HTML, manifest, asset inventory and generated public config before stopping API writers. Keep existing backup, build and migration safety checks.
2. Publish new hashed assets into shared storage before API start. Do not remove any existing assets at this point. Staging failure leaves the serving release unchanged.
3. Perform the existing guarded API/migration cutover and health check, using the image with the matching manifest.
4. Publish the new release's HTML/config together, retaining the prior successful frontend. Use an atomic symlink replacement for normal releases, keeping release directories stable rather than moving their contents. The first migration from the existing real web directory requires an explicit guarded conversion with restoration on failure; do not describe that initial conversion as atomic.
5. Smoke-check representative static and server-rendered pages, runtime config, and referenced assets through Caddy. Only after successful checks record the new current/previous pair.
6. Prune older managed frontend release directories and shared assets outside the union of the two retained inventories. Keep current and previous manifests/inventories/configuration with their releases. A redeployment of the same artifact is still safe and may share all assets.

Track successful publication explicitly; do not infer it from timestamps or arbitrary directories. On any failure before verified publication, do not advance retention or prune. Record an in-progress publication marker before changing live API/frontend state. An unresolved marker is a hard preflight gate blocking another deployment and cleanup until explicit recovery reconciles the running API, frontend pointer and successful-release record. Recovery must not merely delete the marker to bypass reconciliation. Clear the marker only after the verified current/previous record is durably committed; a crash after that commit may be reconciled from those identities. Cleanup retries must verify the active API/frontend match the committed release before pruning. If post-publication checks fail, report the exact serving state and require recovery; do not automatically roll back the database/API after possible writes. A cleanup failure reports the deployment as published but cleanup incomplete, preserves the current/previous record and permits an idempotent retry.

Cleanup is confined to frontend-owned release data and assets. Never recursively delete the existing whole release root: it also contains API, migration and package data. Database backups and Docker image retention remain governed by existing operations. Preserve assets from a failed candidate until a subsequent successful cleanup rather than risking deletion while its API might still serve references.

### First hashed deployment and rollback

The user explicitly accepts a breaking first deployment: existing tabs using unversioned JS/CSS may require refresh immediately after cutover. Do not add a legacy URL serving bridge or copy legacy source assets into the Vite output. Preserve the old frontend/config directory as the previous rollback input, with an explicit legacy record indicating no hashed-asset inventory. That record is not a malformed/missing manifest fallback for hashed releases. Remove the legacy frontend directory when it leaves the two-release window. Subsequent hashed deployments retain current plus previous asset sets normally.

The previous frontend/config and matching API image are rollback inputs, not a promise that frontend rollback alone can reverse an API/database migration. Preserve existing post-write recovery constraints and document the coordinated recovery procedure. New and previous hashed asset sets remain available regardless of the active frontend pointer. Compatibility of old frontend code with a changed API remains a separate application contract.
